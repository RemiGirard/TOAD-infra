# From no cloud account to TOAD access

Start here if you have an app but no cloud account yet. Your coding agent can
guide the journey, prepare local configuration and explain the choices. You
complete the provider's sensitive account, verification and payment steps.
Then the agent can continue with the approved platform and app deployment.

Already have a verified TOAD platform? Reuse it and go to
[Deploy an app](FIRST-APP.md). Do not order another product or create another
project just to follow this guide.

## Choose the cloud

**OpenStack is TOAD's foundation. Infomaniak is its verified production path.**
The current workflow also uses Infomaniak DNS and its certificate automation.
Other OpenStack clouds require a compatibility review, configuration changes
and potentially implementation changes; they are not verified drop-in targets.
See [using another OpenStack cloud](#using-another-openstack-cloud).

The path for a new Infomaniak customer is:

**Customer account → Public Cloud product → project and OpenStack user →
local TOAD context → verified platform → your app.**

These are different things:

| Item | What it is for |
|---|---|
| Infomaniak customer account | Sign in to Manager, own products and manage billing within your organization. |
| Public Cloud product and project | Enable cloud consumption, then isolate resources and project access. |
| Dedicated OpenStack user | Authenticate TOAD to that project; this is separate from your customer login. |
| TOAD context | Keep the project's configuration and credentials isolated on your operator machine. Creating a local context does not provision servers. |

## 1. Create or reuse your customer account

Follow [Infomaniak's account registration guide](https://www.infomaniak.com/en/support/faq/2232/create-an-infomaniak-account).
Use an email address you control and complete the required email verification.
Choose the organization that should own the cloud and receive its invoices.
If you already have access to that organization, use the existing account.

Enter passwords and any verification codes directly in the provider's
interface. Do not send them to TOAD or paste them into an agent conversation.

## 2. Activate Public Cloud and review billing

Use the **Sign Up** link in
[Infomaniak's Public Cloud getting-started guide](https://docs.infomaniak.cloud/getting_started/).
Review the product, organization, payment method and terms before confirming
the order yourself.

As documented on **28 October 2026**, direct ordering requires a credit card.
Infomaniak describes a **20 CHF/EUR temporary card pre-authorization** when
creating the product, including with a Free Tier offer. This checks the card;
it is not a TOAD fee or a credit toward resource usage. Read the current
[pre-authorization explanation](https://www.infomaniak.com/en/support/faq/2927/understanding-public-cloud-bank-pre-authorization)
and [billing rules](https://www.infomaniak.com/en/support/faq/2605/understanding-public-cloud-billing).

Before provisioning, review TOAD's [cost worksheet](COSTS.md), the provider's
current prices and your expected storage, network and backup costs. Resource
consumption is billed separately from account creation. This guide does not
order a product or create billable resources for you.

## 3. Prepare a project and dedicated OpenStack access

In Manager, open your Public Cloud product and follow the official
[project creation guide](https://docs.infomaniak.cloud/getting_started/first_project/create_a_project/).
Reuse a suitable project if you already have one. Check its ownership, choose
the deployment region and review quotas before placing TOAD resources there.

Create or select a dedicated OpenStack user for TOAD using the
[Public Cloud user guide](https://www.infomaniak.com/en/support/faq/2492/manage-public-cloud-users).
The OpenStack username is generated by the provider. Its password is separate
from the customer-account password. The maintained Heat workflow requires a
dedicated password-authenticated user for Heat trust creation; successful
application-credential login alone does not establish deployment readiness.

Complete the new user's password and access approval yourself. Keep the
project and service-user names available for your agent, without disclosing
their credential values.

## 4. Download access configuration and prepare TOAD locally

Follow [Connect to the project](https://docs.infomaniak.cloud/getting_started/first_project/connect_project/)
to download the OpenStack cloud configuration for the selected user and region.
Treat that file as a secret, even if its password field is absent.

Continue with [Prepare your operator context](QUICKSTART.md#1-prepare-your-operator-context).
Create the isolated context first, then place the downloaded `clouds.yaml` in
its ignored `credentials/` directory with permissions restricted to the
operator. Share the local path with your agent, not the file's contents.
TOAD's `setup` command can request the service-user password without echoing it.

The [quickstart](QUICKSTART.md) then covers domain ownership, the restricted
Infomaniak DNS token, registry access, platform provisioning and verification.
Account access alone does not create a working TOAD platform.

## Let your agent guide the setup

Use the [deployment starter prompt](../website/agent-prompt.txt) from your app
repository. If your agent has authorized browser access, it can navigate the
official guides and assist with ordinary form fields using information you
provide. With terminal and file access, it can inspect your app, prepare the
TOAD context and check configuration. Without browser access, it can give you
the exact links and resume when you have completed the provider steps.

| Agent can prepare or explain | Your turn before continuing |
|---|---|
| Check existing account/project access, navigate official setup, explain ownership and costs. | Enter new passwords and complete provider-required email, MFA, CAPTCHA or identity checks. |
| Help review the product order and proposed project permissions. | Complete payment/card authorization, final account agreements and approval of new access. |
| Prepare local context files and read-only readiness checks. | Put credentials into the private provider/local interfaces; never into chat. |
| Show the exact resource and DNS plan, then perform the approved deployment. | Approve the specific spend and DNS changes before infrastructure is created or changed. |

The agent should explain the next hand-off, wait for you, verify the result
and resume from that point. It must not claim that an account is active,
payment succeeded or cloud access works without evidence. TOAD itself does
not register customer accounts, handle payment cards or bypass verification.
The selected agent's tools and confirmation rules still apply.

## Using another OpenStack cloud

TOAD uses standard OpenStack APIs and Heat resource types for compute,
networking, load balancing and DNS. Its current production path is not
provider-neutral: `cloud apply` selects the three-manager profile, requires
Infomaniak DNS access, updates parent records through Infomaniak's API, and
configures Infomaniak DNS-01 certificate issuance and DNS verification.
Changing only `clouds.yaml` does not replace those integrations.

Before adapting another provider, review:

| Area | What must be checked |
|---|---|
| Identity and services | Keystone authentication, project roles and Heat trusts; required Nova, Neutron, Heat, Octavia and Designate resources. |
| Capacity | Three managers, server group, tenant networking, two floating IPs, load balancer/listeners/pools/members/health monitors and a DNS zone. Check each service's quotas. |
| Images and scheduling | Immutable image UUID, flavor, external network and availability zones. Current SSH/inventory code expects the `ubuntu` user. |
| Network and load balancer | IPv4 routing, SSH and Swarm connectivity, TCP 80/443 load balancing and health checks. Check conflicts with the current tenant `10.0.0.0/24` and Swarm `10.20.0.0/16` ranges. |
| DNS and certificates | Current Infomaniak parent DNS, authoritative-server checks and ACME integration need to remain valid or be replaced in code. |
| Evidence | Exercise a disposable environment through platform verification, application deployment/diagnosis and recovery before claiming support. |

`doctor --cloud` checks authentication. `discover` lists flavors, images,
networks, keypairs and compute quotas; it does not establish compatibility or
check all availability-zone, network, load-balancer and DNS requirements.
Other providers remain **unverified** until these differences are addressed
and the complete workflow is validated.
